# Energy Heatmap — аддон для WebCTRL

Аддон для Automated Logic WebCTRL: тепловая карта энергопотребления по счётчикам и месячный отчёт
о доле **расчётных (восстановленных статистикой) значений** по группам счётчиков (E1000, E1100, … E1850).

Написан под WebCTRL (Java 11, Servlet 3.1, Tomcat 9), собирается NetBeans/Ant, ставится как `.addon`.

## Возможности

**Тепловая карта**
- дерево локаций из географического дерева WebCTRL, выбор счётчиков по маскам (по умолчанию `_e1`);
- почасовой вид (строки — дни, столбцы — часы 0–23) и посуточный (недели × дни недели);
- суммирование выбранных счётчиков, цветовая шкала по 95-му процентилю, экспорт в CSV;
- часы без связи и часы с нулевым приростом заполняются медианой «того же часа суток».

**Отчёт Calculated Data Report**
- по каждому гипермаркету и каждой группе счётчиков: наработка, измеренный объём, расчётный объём, процент;
- число счётчиков с задетыми границами месяца и без тренда статуса;
- период — последние полные месяцы (1–24), по умолчанию 1.

## Методика расчёта расчётных значений

1. Данные берутся из тренда `cons_total_net_tn` — накопительные показания счётчика.
   Статус связи — тренд `com_st_min` (имя настраивается), по умолчанию `0` = связи нет, `1` = связь есть.
2. Месячная наработка = показание на конец месяца − показание на начало месяца. Счётчик накопительный,
   поэтому пропуски связи **в середине** месяца на разность не влияют и в расчёт не идут.
3. Объём, потерянный на **границах** месяца (ведущий и замыкающий блоки без связи), восстанавливается
   статистикой и идёт в числитель процента:
   `процент = Σ расчётного объёма / Σ наработки` по счётчикам группы.
4. Восстановление — медиана по тому же часу суток, посчитанная по измеренным дням месяца
   (минимум значений задаётся настройкой `minDaysForMedian`).
5. Если накопительное значение падает (замена/сброс счётчика), потерянный объём тоже восстанавливается
   статистикой, **но в числитель процента не входит**.
6. Все гипермаркеты считаются в зоне `Europe/Moscow`.
7. Если тренд статуса недоступен или не различает состояния (бывает, что он всегда равен `1`),
   признаком обрыва считается **замерший счётчик**: сплошной блок часов в начале/конце месяца,
   где накопительное значение не растёт, длиной не меньше `frozenRunHours` (по умолчанию 12 ч).
   Порог защищает от коротких ночных нулей у счётчиков с нулевым потреблением.

## Требования

- WebCTRL (проверялось на сервере WebCTRL с Tomcat 9);
- JDK 11+;
- NetBeans 29 (или совместимый Ant + задачи NetBeans) — проект NetBeans/Ant;
- два JAR-файла (в репозиторий не входят, см. `lib/README.md`):
  - `directaccess-api-addon-1.7.0.jar` — SDK аддонов WebCTRL (поставляется Automated Logic, **не распространяется**);
  - `json-20251224.jar` — библиотека org.json.

## Готовый аддон

Собранный аддон прикладывается к релизам: **Releases** → `Energyheatmap.addon`.
Ставить без переименования — см. «Установка в WebCTRL».

## Сборка

1. Положить оба JAR в каталог **на уровень выше** папки проекта (так прописано в `nbproject/project.properties`):

   ```
   <parent>/
     directaccess-api-addon-1.7.0.jar
     json-20251224.jar
     Energyheatmap/
       build.xml
       src/  web/  nbproject/
   ```

   Либо поправить пути `file.reference.directaccess-api-addon-1.7.0.jar` и `file.reference.json-20251224.jar`
   в `nbproject/project.properties`.

2. Собрать:

   ```bash
   ant clean dist
   ```

   Проще всего открыть проект в NetBeans и нажать Clean and Build: `nbproject/private/` не хранится
   в репозитории (там локальные пути), и NetBeans создаёт его сам вместе с настройками Ant-задач.

3. Результат: `dist/Energyheatmap_<версия>.war` и его копия `dist/Energyheatmap.addon`.

## Установка в WebCTRL

Устанавливать файл **без переименования — как `Energyheatmap.addon`**: имя файла (папки) задаёт контекст
аддона `/Energyheatmap`, а путь к сервлетам в JSP зашит именно так. Если переименовать, отчёт и тепловая
карта будут получать 403 и «не отображаться».

Встраивание на страницу оператора: **Add-on Content** → *Add-on Name*: `Energyheatmap`,
*Content Path*: `heatmap.jsp`, *Location*: Attached.

Проверка после установки:

```
http://<server>/Energyheatmap/info.xml      → версия аддона
http://<server>/Energyheatmap/heatmap.jsp   → страница (200)
```

## HTTP-эндпоинты

| Метод и путь | Назначение |
|---|---|
| `GET /tree/roots` | корневые локации географического дерева |
| `GET /meters/find?path=<path>&masks=<e1,e2>` | поиск счётчиков по маскам (ищет потомка `cons_total_net_tn`) |
| `GET /browse?refresh=true` | тот же поиск с кэшем |
| `GET /data?id=<trendId>&start=<yyyy-MM-dd>&end=<yyyy-MM-dd>&aggregation=hourly&mode=consumption` | почасовое потребление (дельта накопительного тренда) |
| `GET /data/aggregate?ids=<id1,id2>&start=&end=` | сумма почасового потребления по нескольким счётчикам |
| `GET /settings?action=load` | текущие настройки (JSON) |
| `POST /settings?action=save&minDaysForMedian=…&…` | сохранение настроек |
| `GET /report/calculated-percent?path=<path>&months=<1..24>` | отчёт по группам счётчиков |

Ответ отчёта — массив групп:

```json
[{
  "group": "Промышленный холод E1100",
  "mask": "e11",
  "data": [{
    "year": 2026, "month": 10,
    "totalConsumption": 126725.09,
    "measuredConsumption": 101954.6,
    "calculatedConsumption": 24770.5,
    "resetFilledConsumption": 0.0,
    "calculatedPercent": 19.55,
    "calculatedMeters": 5,
    "metersWithBoundaryGap": 5,
    "metersWithoutStatus": 0,
    "metersFailed": 0,
    "totalMeters": 5
  }],
  "errors": [],
  "diag": ["#tul_e1101 | данные: {DATA=4465} | статус: … | заморозка в начале: 139 ч"]
}]
```

`diag` — диагностика: на чём посчитана группа (тренд статуса или признак замершего счётчика),
сколько часов заморозки на границах, какие записи есть в тренде потребления.

## Настройки

Страница `⚙️ Settings` (`settings.jsp`), файл `config.properties` в каталоге данных аддона (`webapp.data.dir`):

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `minDaysForMedian` | 3 | минимум значений на час суток для надёжной медианы |
| `statusTrendName` | `com_st_min` | имя тренда статуса связи |
| `statusErrorOnZero` | `true` | `0` = связи нет (снять галочку, если на объекте наоборот) |
| `frozenRunHours` | 12 | порог «замершего» счётчика на границе месяца, часов |
| `anomalyCorrectionEnabled` | `true` | заполнять пропуски статистикой в тепловой карте |
| `debugLoggingEnabled` | `false` | подробный лог сервера |
| `zeroThreshold` | 100 | устарело, в расчётах не используется (оставлено для совместимости) |
| `resetThreshold` | 10000 | устарело, в расчётах не используется (оставлено для совместимости) |

## Известные ограничения

- **Тренд статуса может не читаться целиком.** На серверной стороне WebCTRL встречается
  `SystemRuntimeException: Record has unexpected value type of 0` при чтении цифрового тренда за длинный
  период. Поэтому статус читается ещё и по суткам от краёв месяца; сутки, которые не читаются,
  считаются сутками без связи. Тепловая карта и отчёт используют один и тот же источник статуса.
- **Признак замершего счётчика — эвристика.** У счётчиков с объективно нулевым потреблением
  (сезонная нагрузка, отключённое оборудование) блок «без прироста» может быть ложным;
  для этого есть порог `frozenRunHours` и возможность его менять.
- **Скорость отчёта.** Один гипермаркет за один месяц считается 35–55 с (несколько чтений тренда
  на счётчик), при нескольких месяцах время растёт пропорционально.
- Тепловая карта строит выборки по пользовательскому соединению (нужна сессия оператора),
  дерево и отчёт — по корневому.
